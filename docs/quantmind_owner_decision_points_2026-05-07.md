# QuantMind 需要用户决策与调研的重要事项清单

生成日期: 2026-05-07  
用途: 汇总必须由项目所有者亲自决策、调研或确认的关键事项。  
关系: 本文件承接 `docs/quantmind_project_audit_2026-05-07.md`，不是实现方案，而是“决策前置清单”。

## 0. 阅读方式

优先级含义:

- P0: 不确定就不要继续推进自动交易或实盘相关开发。
- P1: 会影响系统架构和后续成本，应在主要闭环开发前定下来。
- P2: 可稍后细化，但最好提前形成原则。

每个决策点建议形成一个明确输出物，例如一页调研结论、一个表格、一条红线规则或一个书面授权边界。没有输出物的“想法”不算已决策。

外部资料说明: 本文件列出若干公开调研入口，作为你后续核验候选，不构成供应商推荐。实时行情、券商接口、量化平台、数据版权、费用和接口稳定性都可能变化，正式选择前必须以供应商当前合同、文档、试用结果和你的券商账户条件为准。

## P0-1. 系统定位与自动化边界

### 你需要决定

QuantMind 到底是:

1. 投研辅助系统。
2. 模拟盘自动交易系统。
3. 半自动实盘系统。
4. 全自动实盘系统。

这四者的工程要求和风险完全不同，不能混在一起开发。

### 为什么重要

当前项目已经有“自动模式”“基金经理决策”“MockBroker”“风控中心”等字样和界面，但真实代码还没有形成从信号到订单的闭环。如果系统定位不先定，后续会继续出现“界面看起来能交易，实际没有闭环”的错位。

### 建议倾向

短期把系统定位为:

> A 股个人自用的智能投研 + 模拟盘验证平台，所有实盘动作先保持 suggest 或 confirm，不进入 full auto。

只有当数据源、回测、模拟盘、风控、审计和实盘接口全部达标后，再考虑自动化实盘。

### 你需要产出

- 一条阶段红线: 当前阶段允许到 suggest、confirm 还是 auto。
- 一条资金红线: 真实资金投入上限。
- 一条人工确认红线: 哪些动作必须人工确认。

## P0-2. 股市实时数据源选择

### 你需要决定

系统实盘级实时行情到底使用什么来源。至少要拆成三层:

- 研究/展示数据源。
- 模拟盘和回测数据源。
- 实盘交易决策数据源。

当前项目使用 `adata` 作为主行情源、`akshare` 作为备用源、`baostock` 作为历史 K 线备用源。这适合原型和研究，但不等于实盘级行情体系。

### 你需要调研的问题

- 是否需要实时 Tick、盘口五档、逐笔成交、逐笔委托、Level-2。
- 延迟要求是多少: 秒级、分钟级还是日频即可。
- 是否覆盖全 A、北交所、ETF、可转债、指数、板块。
- 是否提供稳定交易日历、停复牌、涨跌停、复权、财务、行业分类。
- 是否允许本地存储和二次加工。
- 是否允许用于真实交易决策。
- 是否有调用频率限制、断流处理、历史回补接口。
- 是否能在你的部署环境运行，例如 Linux/Mac/Windows。
- 是否有成本预算。

### 候选方向

| 类型 | 候选示例 | 适合用途 | 主要提醒 |
|---|---|---|---|
| 免费开源接口 | AKShare、adata、BaoStock | 研究、原型、备用验证 | 稳定性、版权、频率限制、字段变动不可控 |
| 量化数据平台 | JoinQuant/JQData、掘金量化等 | 研究、回测、部分实时数据 | 需要核验费用、额度、是否可本地化、是否支持实盘 |
| 券商终端接口 | miniQMT/XtQuant、Ptrade 等 | 实盘行情和交易候选 | 强依赖券商、系统环境、账户权限 |
| 自建多源聚合 | 免费源 + 付费源 + 券商源 | 长期稳定架构 | 工程成本最高，但可控性最好 |

### 建议倾向

- 短期: 保留当前免费源，但只作为研究和前端展示，不作为自动下单依据。
- 中期: 选一个稳定的本地化数据源用于回测和模拟盘。
- 实盘前: 使用券商或合规行情服务作为交易依据，并建立免费源/备用源对账。

### 调研入口

- AKShare GitHub: https://github.com/akfamily/akshare
- miniQMT XtData 行情模块: https://www.miniqmt.com/api/miniQMT/miniQMT%E5%AE%98%E6%96%B9API%E6%96%87%E6%A1%A3XtQuant.XtData%E8%A1%8C%E6%83%85%E6%A8%A1%E5%9D%97.html
- JoinQuant 数据服务: https://www.joinquant.com/data
- 掘金量化行情数据文档: https://myquant.cn/docs/l3333/912

### 你需要产出

一个数据源调研表，至少包含:

- 实时行情能力。
- 历史数据能力。
- 覆盖品种。
- 延迟。
- 稳定性。
- 费用。
- 授权限制。
- 本地存储限制。
- Python/API 可用性。
- 试用结果。

## P0-3. 实盘券商接口选择

### 你需要决定

未来是否要接实盘。如果要接，优先接哪类接口:

- miniQMT/XtQuant。
- Ptrade。
- vn.py gateway。
- 掘金量化终端。
- 券商自有 API。
- 暂不接实盘，只做模拟和投研。

### 为什么重要

交易接口决定:

- 操作系统。
- 部署方式。
- 账户类型。
- 能否获取成交回报。
- 能否自动撤单。
- 是否支持融资融券。
- 下单失败如何返回。
- 是否能在你的券商账户上开通。

当前代码只有 `IBroker` 和 `MockBroker`。`config/broker.yaml` 中 QMT/VNPy 只是占位。

### 调研提醒

- 很多券商接口依赖 Windows 客户端常驻。
- 有些接口只对特定券商或特定资产量开放。
- 实盘 API 不只是下单，还要有资金、持仓、委托、成交、撤单、错误回报、断线重连。
- 自动下单前必须先完成只读账户同步。

### 建议倾向

如果目标是个人自用 A 股，优先调研 miniQMT/XtQuant 或你的实际券商支持的自动交易接口。vn.py 可以作为长期框架参考，但要确认 A 股股票接口和你的券商是否实际可用。

### 调研入口

- miniQMT XtTrader 交易模块: https://miniqmt.com/api/miniQMT/miniQMT%E5%AE%98%E6%96%B9API%E6%96%87%E6%A1%A3XtQuant.XtTrader%E4%BA%A4%E6%98%93%E6%A8%A1%E5%9D%97.html
- vn.py 官网: https://www.vnpy.com/
- vn.py 交易接口文档: https://www.vnpy.com/docs/cn/community/info/gateway.html
- 掘金量化 Python SDK/API: https://myquant.cn/docs/python/python_sdk

### 你需要产出

- 目标券商和账户类型。
- 接口开通条件。
- 是否能读取账户/持仓/委托/成交。
- 是否能报单/撤单。
- 是否支持模拟账户。
- 接口运行环境。
- 最小可行接入路径。

## P0-4. 真实资金风险边界

### 你需要决定

- 初始实盘资金上限。
- 单笔交易金额上限。
- 单只股票最大仓位。
- 总仓位上限。
- 每日亏损熔断线。
- 每周/月亏损暂停线。
- 最大持仓数量。
- 是否允许隔夜持仓。
- 是否允许追涨、涨停买入、跌停卖出。

### 为什么重要

### 建议倾向

在没有 3 到 6 个月模拟盘证据前:

- 真实资金为 0。
- 自动下单为 0。
- 只允许模拟盘闭环。

模拟盘达标后，实盘也应从小额 confirm 模式开始。

### 你需要产出

一份风险参数确认表，并明确哪些参数绝不允许由 LLM 修改。

## P0-5. 第一阶段策略范围

### 你需要决定

第一阶段到底交易什么策略。不要一开始追求“全市场全自动智能交易”。

可选范围:

- 只做 watchlist 中的 5 到 20 只熟悉股票。
- 只做大盘 ETF。
- 只做行业 ETF。
- 只做大市值高流动性股票。
- 只做日线级别，不做分钟级。
- 只做买入/持有/卖出建议，不做做空。

### 为什么重要

A 股 T+1、涨跌停、停牌、滑点和交易时段限制会让“看起来能做的策略”在实盘中完全变形。策略范围越窄，越容易先把闭环做扎实。

### 建议倾向

第一阶段建议:

- 只做日频或低频。
- 只做 long-only。
- 只做高流动性标的。
- 只做 watchlist。
- 不做盘中高频自动交易。

### 你需要产出

一个 `Phase-1 Universe` 清单:

- 股票/ETF 范围。
- 排除规则。
- 调仓频率。
- 最大持仓数。
- 是否允许新股、ST、北交所、可转债、创业板、科创板。

## P0-6. “LLM 的角色”边界

### 你需要决定

大模型在系统中到底是:

- 数据提取器。
- 投研解释器。
- 事件推演器。
- 策略假设生成器。
- 最终交易决策者。
- 自动下单者。

这些角色风险完全不同。

### 为什么重要

当前系统把 `fund_manager` 的 JSON 输出保存为交易信号，但没有足够的策略规则、回测、风控闭环。让 LLM 直接决定买卖和仓位风险很高。

### 建议倾向

LLM 应该做:

- 信息抽取。
- 事件归纳。
- 隐性变量推演。
- 多视角辩论。
- 决策解释。
- 异常原因复盘。

LLM 不应该直接做:

- 最终资金安全判断。
- 仓位硬限制。
- 自动下单。
- 止损触发。
- 熔断判断。

### 你需要产出

一条 LLM 权限边界:

> LLM 可以建议，但任何真实或模拟订单都必须通过确定性策略规则、RiskEngine 和授权模式。

## P0-7. Kimi thinking 模式使用策略

### 你需要决定

哪些场景允许使用 Kimi thinking，哪些场景必须禁用。

### 为什么重要

项目已经暴露出 Kimi thinking 可能导致超长等待。长等待不仅影响体验，还会拖垮 watchlist 批处理、成本预算和交易时效。

### 建议倾向

- 快速日常扫描: 禁用 Kimi thinking。
- 常规 watchlist 分析: 便宜模型先做，只有低置信度或重大事件升级 Kimi。
- 盘后深度复盘: 可允许 Kimi thinking。
- 实盘下单前: 不应等待长 thinking 才能止损或执行硬风控。

### 你需要产出

一张模型使用矩阵:

| 场景 | 模型 | thinking | 超时 | 失败降级 |
|---|---|---|---|---|
| 新闻摘要 | DeepSeek/Qwen | 关闭 | 待定 | 跳过或备用 |
| 快速选股 | Qwen/DeepSeek | 关闭 | 待定 | 仅生成候选 |
| 深度争议分析 | Kimi | 可开 | 待定 | 回退 Qwen |
| 最终下单风控 | 代码 | 不适用 | 秒级 | fail closed |

## P1-1. 新闻与资讯源覆盖范围

### 你需要决定

除了行情，系统还需要哪些信息源:

- 财经新闻。
- 公司公告。
- 财报。
- 交易所问询。
- 政策文件。
- 宏观数据。
- 行业数据。
- 研报。
- 龙虎榜。
- 北向资金和主力资金。
- 社交媒体和论坛情绪。

### 为什么重要

当前项目新闻源较窄，主要是 akshare 的 Eastmoney 新闻接口。对于“隐性信息汇总推演”来说，单一新闻源无法支撑高质量推断。

### 建议倾向

优先级:

1. 公司公告和交易所信息。
2. 财经新闻。
3. 行业和宏观数据。
4. 资金流和龙虎榜。
5. 社交情绪。

不要一开始接过多低质量社交源，否则噪声会压过信号。

### 你需要产出

资讯源清单:

- 来源。
- 更新频率。
- 是否可机器读取。
- 是否允许保存。
- 是否有付费或版权限制。
- 对选股的预计价值。

## P1-2. 回测与模拟盘验收标准

### 你需要决定

什么结果算“可以进入下一阶段”。

### 需要定义的指标

- 回测年化收益。
- 最大回撤。
- Sharpe。
- 胜率。
- 盈亏比。
- 换手率。
- 交易成本后收益。
- 相对沪深 300 或中证 500 的超额收益。
- 模拟盘连续运行天数。
- 交易失败率。
- 信号命中率。
- Kimi 超时率。

### 建议倾向

不要只看收益率。至少同时看:

- 最大回撤。
- 交易次数。
- 成本后收益。
- 基准超额。
- 收益稳定性。
- 极端日表现。

### 你需要产出

一份“阶段门槛”:

```text
满足以下条件才允许从模拟盘进入 confirm:
- 模拟盘连续运行 X 天。
- 系统无 P0 故障。
- 最大回撤低于 X%。
- 数据缺失率低于 X%。
- 订单失败率低于 X%。
- 所有交易可追溯到决策记录。
```

## P1-4. 前端优先工作流

### 你需要决定

前端首先服务哪个核心工作流:

1. 大盘监控。
2. Watchlist 分析。
3. 订单审批。
4. 模拟盘组合。
5. 复盘报告。
6. 设置和监控。

### 为什么重要

当前前端页面很多，但关键操作有半接线状态。例如批准/拒绝只是 toast，Simulation 的“注入 Agent 辩论”只是跳转。

### 建议倾向

优先做真实闭环页面:

```text
Watchlist -> 触发分析 -> 查看决策 -> 生成订单意图 -> 风控检查 -> 人工审批 -> 模拟成交 -> 复盘
```

界面漂亮是加分项，但当前最重要的是每个按钮都真实有效。

### 你需要产出

一张用户旅程图，标出哪些按钮必须真实接后端，哪些可以暂时隐藏。

## P1-5. 数据保存、隐私与密钥管理

### 你需要决定

- LLM key 放哪里。
- 券商账号密码放哪里。
- 是否允许前端修改关键配置。
- MongoDB 和 Redis 是否只绑定本机。
- 决策记录保留多久。
- 影子对比记录保留多久。
- 是否需要备份。
- 是否需要加密。

### 为什么重要

一旦接实盘，系统里会出现券商账户、交易记录、模型路由、收益和资金信息。这些都不能按普通开发项目处理。

### 建议倾向

- LLM key 和券商 key 只走环境变量或本机安全存储。
- 前端不能直接写入高危配置，至少需要本机鉴权。
- 所有真实订单和授权变更必须写审计日志。
- 实盘前必须加登录和权限控制。

### 你需要产出

一份安全策略:

- 密钥位置。
- 可访问人员。
- 备份策略。
- 数据保留时间。
- 是否加密。
- 是否允许远程访问。

## P2-1. MiroFish 的真实使用范围

### 你需要决定

MiroFish 是:

- 日常每只股票都跑。
- 只在重大事件触发。
- 只做盘后复盘。
- 只做研究展示。

### 为什么重要

MiroFish 隐性变量推演成本高、耗时长，并且当前代码默认没有运行时接线。盲目开启会放大成本和延迟。

### 建议倾向

只在重大事件触发，且不直接决定下单。MiroFish 输出应作为情报证据之一，而不是最终交易命令。

### 你需要产出

- 触发条件。
- 预算上限。
- 超时上限。
- 是否允许注入最终决策。
- 是否必须人工复核。

## P2-2. 自进化机制边界

### 你需要决定

所谓“自进化”允许系统自动改变什么:

- 调整候选池权重。
- 调整模型路由。
- 调整 prompt。
- 调整策略参数。
- 调整风控参数。
- 调整实盘下单规则。

### 风险提醒

风控参数、下单规则、实盘权限不应由系统自动修改。  
自进化应该先从“提出建议”和“离线验证”开始。

### 建议倾向

允许自动生成改进建议，不允许自动部署到实盘。  
任何策略参数变化必须经过回测和人工确认。

### 你需要产出

一条自进化授权边界:

```text
系统可以自动学习和提出策略候选，但不能自动修改实盘风控与交易权限。
```

## P2-3. 模型供应商与模型组合

### 你需要决定

是否继续使用当前三模型组合:

- DeepSeek。
- Qwen。
- Kimi。

还是增加/替换:

- OpenAI。
- Claude。
- 本地模型。
- 其他国内模型。

### 为什么重要

模型选择影响:

- 成本。
- 延迟。
- 稳定性。
- JSON 可控性。
- 中文金融能力。
- 上下文长度。
- 隐私风险。

### 建议倾向

不是模型越强越好。应按任务分层:

- 摘要和清洗: 便宜模型。
- 候选排序: 中等模型。
- 重大争议和盘后复盘: 强模型。
- 风控硬限制: 代码。

### 你需要产出

模型路由表，并附带每类任务的成本和超时限制。

## P2-4. 监控与告警渠道

### 你需要决定

系统异常时通知到哪里:

- 本机日志。
- Web UI。
- 邮件。
- 企业微信/钉钉/飞书。
- 手机推送。

### 需要监控的事件

- 行情源断流。
- 新闻源失败。
- LLM 全部不可用。
- Kimi 超时率过高。
- 每日预算超限。
- 分析任务失败。
- 订单失败。
- 熔断触发。
- 真实账户持仓和系统记录不一致。

### 建议倾向

实盘前必须有外部告警渠道，不能只靠看前端页面。

### 你需要产出

- 告警渠道。
- 告警等级。
- 每个等级的处理动作。

## P2-5. 是否需要移动端或远程访问

### 你需要决定

是否需要在外部网络访问系统，或者只在本机/内网使用。

### 风险提醒

一旦开放远程访问，就必须处理:

- 登录认证。
- HTTPS。
- CSRF。
- API 权限。
- 密钥隔离。
- 审计日志。
- 防止外部触发昂贵 LLM 任务或交易动作。

### 建议倾向

实盘前保持本机或可信内网。远程访问可以晚一点做。

### 你需要产出

网络访问边界:

- 本机。
- 局域网。
- VPN。
- 公网。

## 建议的决策顺序

建议按以下顺序推进，不要跳级:

1. 定系统定位和自动化边界。
2. 定真实资金风险边界。
3. 定第一阶段交易标的范围。
4. 调研并确定实时行情和历史数据源。
5. 调研券商接口，但先只做只读验证。
6. 定 LLM 权限和 Kimi thinking 使用边界。
7. 定回测和模拟盘验收标准。
8. 定前端核心工作流。
9. 定数据安全和备份策略。
10. 再开始实盘接口和自动化交易开发。

## 建议你近期完成的 5 个调研输出

### 1. 数据源对比表

目标: 明确实盘前到底信任哪个行情源。  
建议字段: 覆盖范围、延迟、稳定性、成本、授权、API、试用结论。

### 2. 券商接口可行性表

目标: 明确你的真实券商账户能否程序化交易。  
建议字段: 券商、接口、开通条件、系统要求、行情能力、交易能力、回报能力。

### 3. 第一阶段策略范围说明

目标: 避免系统从一开始就做过宽。  
建议字段: 标的池、频率、仓位、排除规则、调仓规则。

### 4. 风险红线确认表

目标: 所有代码默认值都要被你的真实风险边界替代。  
建议字段: 单股仓位、总仓位、单日亏损、月亏损、最大交易次数、kill switch。

### 5. LLM 使用边界表

目标: 防止 Kimi thinking 和大模型权限失控。  
建议字段: 任务、模型、thinking、超时、预算、失败降级、是否允许影响订单。

## 最后提醒

这个项目最大的问题不是“智能不够”，而是“闭环不够硬”。  
在你完成 P0 决策前，继续增加 Agent、Prompt 或仿真复杂度，收益有限，风险会继续累积。优先把数据源、交易边界、风控红线、模拟盘闭环和复盘标准定下来，后续代码才有明确方向。
